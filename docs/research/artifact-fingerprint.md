# Research: deterministic exact-byte TF artifact fingerprints

Issue: #7

## Scope

Define a shared, portable identity for the exact files that constitute a generated Text-Fabric artifact. This identity is for reproducibility/integrity of shipped bytes, not operational run metadata, source provenance, semantic equivalence, or release certification.

## Consumer evidence

### CopticScriptorium-TF

The current writer removes Text-Fabric's volatile `@dateWritten` header before publication. That normalization happens at the writer boundary, before any identity is computed, so a raw-byte fingerprint can truthfully identify the bytes that actually ship.

### TLHdig-TF

The current `tlhdig-current-tree-v2` manifest hashes `.tf` files after skipping `@dateWritten`. Its own reproducibility research explicitly distinguishes that canonical/logical output identity from raw artifact-byte equality and uses ordinary SHA-256 for the latter.

This distinction must remain visible in tf-build: the generic fingerprint must not silently normalize TF content.

### ORACC-TF

`programs/oracc_tf/distribution.py` already has a useful predecessor:

- recursively enumerates regular files;
- rejects symlinks;
- uses stable relative POSIX paths;
- hashes path + NUL + payload length + raw payload bytes;
- stores the tree digest in immutable release records;
- detects changed bytes under the same release identity.

Its distribution-specific digest is intentionally opaque (aggregate only) and has no explicit algorithm-domain/version separator. The shared package should retain its strong closed-tree/raw-byte properties while making per-file evidence and algorithm evolution explicit.

## Exact bytes, not canonical semantics

The shared algorithm hashes the actual bytes on disk. It does not:

- skip or rewrite `@dateWritten`;
- normalize newlines;
- normalize Unicode;
- parse/re-serialize JSON/YAML/TF;
- ignore auxiliary shipping files because they are not `.tf`.

A project that wants deterministic raw identity must first make its generated bytes deterministic. Coptic's timestamp stripping is an example. A project that wants a logical/canonical identity must use a separately named consumer-specific algorithm.

## Artifact boundary

The artifact root is a real directory, not a symlink.

Closed-world enumeration includes every regular file recursively except two fixed derived/recursive classes:

1. any subtree whose path component is exactly `.tf`, Text-Fabric's compiled cache directory;
2. the canonical root manifest file `tf-build-manifest.json`, because hashing the manifest that contains its own digest is recursive.

Everything else counts: `*.tf`, LICENSE, README/docs shipped inside the artifact, provenance/config files, and arbitrary other regular auxiliary files.

Symlinks and non-regular filesystem entries fail closed rather than being dereferenced or ignored. Empty directories do not contribute; the identity is a file-tree identity.

## Paths

Manifest paths are strict UTF-8, POSIX-relative paths from the artifact root.

- no absolute paths;
- no host checkout/output prefix;
- no `.` or `..` components;
- no separator normalization beyond representing filesystem-relative components with `/`;
- no Unicode normalization: changing the actual filename changes artifact identity;
- paths are sorted by their UTF-8 byte sequence for an explicit cross-platform order.

A filename that cannot be encoded as strict UTF-8 is rejected because it cannot participate portably in the JSON manifest contract.

## Per-file identity

Each included file records:

- `path`;
- exact byte count;
- `sha256:<64-lowercase-hex>` over the exact file bytes.

SHA-256 is sufficient for reproducible artifact integrity and is already used by TLHdig/ORACC. The schema names it explicitly so a future algorithm can be introduced under a new schema/algorithm identifier rather than changing meaning in place.

## Aggregate identity

Use a separate SHA-256 accumulator with domain/version separation:

`tf-build-artifact-tree-v1\0`

For each file in path-byte order, feed unambiguous binary fields:

- 8-byte big-endian path-byte length;
- path UTF-8 bytes;
- 8-byte big-endian file byte length;
- raw 32-byte SHA-256 file digest.

The aggregate becomes `sha256:<hex>`.

This avoids ambiguity between path/content boundaries, makes the aggregate independent of JSON formatting, and prevents the same record stream being confused with another future tf-build digest algorithm.

## Manifest

Schema 1 machine representation:

```json
{
  "schema": 1,
  "algorithm": "tf-build-artifact-tree-v1",
  "digest": "sha256:...",
  "files": [
    {"path": "otype.tf", "bytes": 123, "sha256": "sha256:..."}
  ]
}
```

The file list is already canonical; JSON serialization also uses sorted keys, UTF-8, `ensure_ascii=False`, and one trailing newline.

The manifest contains no timestamps, absolute paths, source identity, validation claims, producer/version, or operational metrics. Those belong to #5 or a consumer release record that composes this fingerprint.

## Computing vs writing

Keep computation pure with respect to the artifact tree:

- `fingerprint_tf_artifact(root)` returns the immutable in-memory manifest and never writes files.
- a separate writer may serialize it to the canonical root `tf-build-manifest.json` using safe atomic file replacement semantics.
- recomputation automatically excludes that canonical manifest filename, so writing it does not change the digest.

Verification should recompute the current tree and compare the complete manifest, not only the aggregate string, so changed/missing/extra files are diagnosable.

## Mutation and filesystem boundary

The normal caller is a private `BuildWorkspace` staging tree after conversion/validation and before publication. Hostile concurrent mutation is outside the repository's filesystem sandbox contract.

Still, the implementation should fail if an included entry changes type/disappears while being hashed. It must never follow a symlink encountered during enumeration/opening.

A full transactional filesystem snapshot is not required for schema 1.

## Relationship to #5 and #6

- #5 reports operational run metadata and declared Git provenance.
- #6 proves the generated TF tree structurally/runtime loads.
- #7 identifies the exact shipping bytes after validation.
- a consumer can compose their outputs into a release record, but tf-build does not conflate them.

## Non-goals

- source-tree identity;
- semantic-equivalence hashing;
- canonicalized TF hashing;
- signing/attestation;
- historical release ledger;
- dependency lock identity;
- browser/app semantic validation.
