# Actual converter adoption of tf-build

**Evidence checked: 2026-11-17.** This matrix counts *production calls in independent converter repositories*. It deliberately distinguishes merged/operational consumers from unmerged migrations, tests-only imports and planned integrations. It is not a ranking of scholarly TF coverage or a claim that every converter uses every helper.

## Release and integration constraints

The usable dependency here is the immutable [GitHub Release `v0.1.0rc1`](https://github.com/alexsosn/tf-build/releases/tag/v0.1.0rc1), with published wheel SHA256
`dff2a14c0299422b4716217d04e6d43b47e714f4dacdb21d9939292051e82c9a`. A GitHub wheel direct-reference installation is not proof of a PyPI upload. The current `0.1.0rc2` source version is **not published**. The immutable rc1 wheel has a known runtime `tf_build.__version__` discrepancy; for rc1, use `importlib.metadata.version("tf-build")` as the installed distribution identity.

For each subsequent migration, verify both the *declared, actually installable dependency* and a real production call site. Preserve consumer-specific corpus semantics, source provenance, licenses, TF ontology, Text-Fabric writer behavior and user interface. Run test-first migration contracts, original-source native TF reload or Agora/installed-user smoke, exact-head CI and a logically independent adversarial review before merging. Shared functions are infrastructure boundaries, not automatic certification of Coptic↔Greek translation alignment or corpus correctness.

See [milestone #112](https://github.com/alexsosn/tf-build/issues/112) and [development procedure](agentic-dev-loop.md) for the ongoing consumer-driven work.
